# 10a: Ticket data model, lanes and the create-ticket function

Type: task
Status: ready-for-agent
**Blocked by:** 02

**What to build:** Give tickets a real, DB-owned shape and a single way to create them. Today a ticket is just a `conversations` row (`type = 'group'`, `ticket_number IS NOT NULL`, columns added in `041_parish_tickets_and_messaging_rls.sql`) that the browser inserts directly in `submitParishOfficeInquiry` (`web/src/lib/supabase/messaging.ts` ~1739). The browser generates `ticket_number` itself (`TCK-${Date.now().toString().slice(-6)}`, collision-prone), picks the participants itself, and falls back to **localStorage** (`saveLocalMinistryConv`) when the insert fails, which creates "tickets" no staff member can ever see. The RLS insert policy (`040_allow_parish_inquiries.sql`) lets any signed-in user create any `group` conversation for any church. The Direct-message rule that used to sit in this ticket is now ticket 10b; the two are independent and can be built in either order.

Ordering note: the new functions call `assert_account_active()` (ticket 07, spec decision 26). If ticket 07 has already shipped, call it first in every new `SECURITY DEFINER` function here; if not, ticket 07's sweep over `authenticated`-granted functions adds it.

Migration (next free number; append to `APPLY_ALL_MIGRATIONS.sql`; additive only):
1. `ALTER TABLE public.conversations ADD COLUMN`: `ticket_lane text` (`'church'` or `'platform'`, CHECK; NULL for non-tickets), `assigned_to uuid REFERENCES public.profiles(id) ON DELETE SET NULL`, `escalated_at timestamptz`, `reopen_count smallint NOT NULL DEFAULT 0`, `linked_ticket_id uuid REFERENCES public.conversations(id) ON DELETE SET NULL`, `sent_back_at timestamptz` (set by ticket 14). Backfill `ticket_lane = 'church'` for every existing row with a `ticket_number`. Add `CHECK (ticket_number IS NULL OR ticket_lane IS NOT NULL)`.
2. A sequence `public.ticket_number_seq` and a generated number `'TCK-' || lpad(nextval(...)::text, 6, '0')`, unique index on `ticket_number`.
3. `SECURITY DEFINER` function `public.create_ticket(p_lane text, p_church_id uuid, p_category text, p_subject text, p_message text, p_linked_ticket_id uuid DEFAULT NULL, p_subject_user_id uuid DEFAULT NULL) RETURNS uuid` (pattern: `046_appointment_changes_and_cancel.sql`; `GRANT EXECUTE` to `authenticated` only). It validates in the database what the web only hinted at:
   - `church` lane: caller is a Parishioner or Volunteer; `p_church_id` is a real church **that has at least one Church Admin**, otherwise reject with "This church has no administrator yet. You can report a concern about the church instead." (spec decision 36; add `public.church_has_admin(_church_id uuid) RETURNS boolean` so the form can ask). Participants: the requester plus the church's **Church Admins only**. Priests and Volunteers are **not** added (today `submitParishOfficeInquiry` adds them); they gain access only through assignment (ticket 13), per the privacy rule (spec decision 25). `admin` no longer exists after ticket 02.
   - `platform` lane: caller is **church staff: a Church Admin, a Priest or a Volunteer**; `church_id` is the caller's own church; participants: the requester plus the single Super Admin (`role = 'super_admin'`). **Allowed categories per role (spec decision 28) come from one list inside the function**: Church Admin `general`, `user_deletion_request` (enabled by ticket 17), `church_setup` ("Church verification and setup"), `report_problem`, `report_person` ("Report a person or abuse"); Priest and Volunteer `general`, `report_problem`, `report_person`. Any other category for a role is rejected, and only a Church Admin can use `user_deletion_request`. A **Parishioner** may create a platform ticket only with category `report_church` ("Report a concern about my church", spec decision 34): it goes straight to the Super Admin, `p_church_id` is the church the concern is about (any real church; it needs no Church Admin), and its participants are the requester and the Super Admin only, so that church's Church Admin never sees it. **Rate limits (decisions 30, 34, 39):** reject with a clear error when the caller already has the maximum of platform tickets whose status is `open` or `in_progress` (resolved and closed ones do not count): **3** platform tickets per person **not counting `user_deletion_request`** ("You already have 3 open tickets with the Super Admin. Wait for a reply or close one before raising another."); **5** open `user_deletion_request` tickets per Church Admin ("You already have 5 open deletion requests. Wait for the Super Admin to decide on one before filing another.", enforced here and enabled by ticket 17); **2** open `report_church` concerns per Parishioner ("You already have 2 open concerns. Wait for a reply before raising another."). The check and the insert run under a per-caller advisory lock (`pg_advisory_xact_lock(hashtext(auth.uid()::text))`) so two simultaneous requests cannot both slip past the limit. The church lane has no limit. **Privacy (decision 29):** the participants of a platform ticket are the requester and the Super Admin only; the requester's own Church Admin is never added and cannot read it (the read predicate is ticket 11).
   - **Parishioners can create a `platform` ticket only as `report_church`**; a Church Admin and a Priest cannot create a `church` ticket (a Volunteer can create either lane); nobody can create a ticket as the Super Admin.
   - Subject at least 3 and message at least 10 characters (the rules already in `submitParishOfficeInquiry`); on the `church` lane `p_category` must be one of the existing ids in `INQUIRY_CATEGORIES` (`web/src/components/churches/ParishInquiryModal.tsx`); on the `platform` lane it must be in the per-role list below. `user_deletion_request` is rejected until ticket 17 ships.
   - Inserts the conversation, participants and the first message in one transaction. Returns the conversation id.
   - **Changing home church (spec decision 40, accepted behaviour):** a ticket's `church_id` is fixed when it is created, and the read predicate (ticket 11) uses the ticket's `church_id`, not the requester's current church. A Parishioner who changes home church keeps their open tickets with the old church (its Church Admin still handles them) until they are closed; new tickets go to the new church. Do not move or reassign open tickets on a church change.
4. Tighten the `conversations` INSERT policy so a row with `ticket_number IS NOT NULL` can no longer be inserted by `authenticated` directly (`create_ticket` is `SECURITY DEFINER` and still can). Direct, channel and ministry-group creation is unchanged.

- [ ] A Parishioner or Volunteer creates a ticket for a church and the Church Admin of that church can open it; the number is `TCK-######` from the sequence. Its only participants are the requester and the church's Church Admins (no Priest or Volunteer rows).
- [ ] A Church Admin, Priest or Volunteer creates a platform ticket; only the requester and the Super Admin can read it (other church staff cannot).
- [ ] A Parishioner cannot create any platform ticket except `report_church`, a Church Admin or Priest cannot create a church-lane ticket, and a direct `INSERT` of a ticketed conversation through REST is rejected.
- [ ] **Categories:** each role can raise only its own platform categories (a Priest cannot raise Church verification and setup or Request user deletion; a Parishioner can raise only `report_church`).
- [ ] **Rate limits:** a person with 3 Open or In Progress platform tickets (not counting deletion requests) cannot create a fourth and sees the clear error; resolving or closing one lets them create another; two simultaneous attempts at the limit create at most 3. A Church Admin is limited to 5 open deletion requests independently of the 3 (a sixth is refused; deletion requests do not use up the 3), and a Parishioner to 2 open `report_church` concerns.
- [ ] **Privacy:** a staff member's platform ticket cannot be read by their own Church Admin, by other staff, or by another church's Church Admin; only the requester and the Super Admin. A Parishioner's `report_church` concern is invisible to the Church Admin of the church it is about.
- [ ] **Church without a Church Admin:** a church-lane ticket for a church with no Church Admin is rejected with "This church has no administrator yet"; `report_church` for the same church still works.
- [ ] **Changing home church:** a Parishioner who changes home church keeps their open tickets with the old church (its Church Admin still reads and handles them) and a new ticket goes to the new church.
- [ ] Existing tickets keep working and read as `church` lane.
- [ ] If creation fails the user sees the error and nothing is stored locally.
