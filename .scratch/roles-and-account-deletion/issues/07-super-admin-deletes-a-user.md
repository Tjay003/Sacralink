# 07: Super Admin deletes a user (anonymize foundation)

Type: task
Status: ready-for-agent
**Blocked by:** 02, 05

**What to build:** The deletion engine and its first caller. The Super Admin can delete any user except themselves. "Delete" means **anonymize in place**: the `profiles` row and the `auth.users` row are kept, because the FKs cascade from them (`profiles.id` to `auth.users` ON DELETE CASCADE in `001`; `appointments.user_id` in `008`; donations, `messages.sender_id` in `027`, conversation members and `notifications` cascade from `profiles`). Deleting the auth user would erase the appointments, donations and messages we must keep.

Migration (next free number; add to `APPLY_ALL_MIGRATIONS.sql`):
1. `ALTER TABLE public.profiles ADD COLUMN deleted_at timestamptz` (plus an index on `deleted_at IS NOT NULL` if needed).
2. An internal `SECURITY DEFINER` function `public.anonymize_user(p_user_id uuid)` (not granted to `authenticated`) that, in one transaction:
   - sets `profiles.full_name = 'Deleted User'`, clears `email`, `phone`, `avatar_url`, address and any other personal fields (check the `profiles` columns in `web/src/types/database.ts`), `role = 'user'`, `is_priest = false`, `assigned_church_id = NULL`, `church_id = NULL`, `deleted_at = now()`;
   - rewrites `auth.users.email` to a unique unusable value (for example `deleted+<uuid>@deleted.invalid`), clears phone and metadata, sets `banned_until = 'infinity'`, and deletes the user's rows from `auth.sessions`, `auth.refresh_tokens` and `auth.identities`, so they are signed out at once and can never log in;
   - removes the user's future-looking personal data that should not outlive them: `notifications`, push tokens if a table exists, `priest_availability` rows, open conversation memberships that are not parish channels (verify the table names in migrations `017`, `027`, `042`);
   - cancels the user's own **pending** appointment requests (they can never be served) with reason "Account deleted", through the existing cancel path or a direct status update inside the function; approved appointments stay as history;
   - **closes the user's open tickets**: every conversation with `ticket_number IS NOT NULL` and `created_by = p_user_id` whose `status <> 'closed'` is set to `closed`, and one `message_type = 'system'` note is written in each (sender = the deleted user's id, metadata `{event: 'ticket_closed_account_deleted'}`, text "The requester's account was deleted"). The ticket-flow column lock (ticket 11) does not block this because the function is `SECURITY DEFINER`; the notifications and any assignee links for those tickets need no cleanup (ticket 16 and ticket 11's live handler check cover them);
   - calls `public.cleanup_staff_assignments(p_user_id, <their church>)` (ticket 05; ticket 13 later extends it to unassign their assigned church tickets) before clearing the church columns, so a deleted staff member leaves the staff channel and (once 13 ships) their assigned tickets go back to the Church Admin; their own open platform tickets are closed by the step above, as for any user;
   - writes one `activity_logs` row (`action = 'user_deleted'`, who requested it).
3. A public wrapper `public.delete_user_account(p_user_id uuid)` granted to `authenticated` that only allows `super_admin` callers, rejects deleting yourself, rejects deleting a `super_admin` row, and calls `anonymize_user`.
4. **Instant cut-off for blocked accounts (spec decision 26).** Banning the auth user and deleting `auth.sessions` / `auth.refresh_tokens` stops new logins and refreshes, but PostgREST keeps accepting an access token that was already issued until `jwt_expiry` (3600 s in `supabase/config.toml`). Make the cut-off immediate in the same migration:
   - `public.is_account_blocked() RETURNS boolean` (`SECURITY DEFINER`, `STABLE`, fixed `search_path`, `GRANT` to `authenticated`): true when the caller's profile (`auth.uid()`) has `deleted_at IS NOT NULL`. It is a thin wrapper over `public.is_user_blocked(_user_id uuid) RETURNS boolean` (same attributes, reads `profiles.deleted_at`); ticket 19 redefines `is_user_blocked` to also cover `suspended_at`. Also `public.assert_account_active()` that raises `42501` "This account is blocked" when it is true.
   - **No messages to a blocked user (spec decision 38).** `public.direct_other_participant_blocked(_conversation_id uuid) RETURNS boolean` (`SECURITY DEFINER`, `STABLE`): true for a `type = 'direct'` conversation whose other participant (not `auth.uid()`) satisfies `is_user_blocked`. A `RESTRICTIVE` INSERT policy on `public.messages` rejects a message in such a conversation ("This user is no longer available"). Expose the flag in the conversation list query so ticket 12 can disable the composer. It covers deleted users now and suspended users once ticket 19 extends `is_user_blocked`. Storage and every table stay in the cut-off scope above.
   - Redefine `public.get_current_user_role()` and `public.get_current_user_church_id()` (`024`, last redefined in `034`; about 100 policies call them) to return `NULL` for a blocked account, and add the blocked check to `public.can_access_conversation`, `public.can_access_conversation_by_id`, `public.is_staff_channel` (`059`) and `public.is_conversation_participant` (`027`). `public.get_user_role(uuid)` (`036`) reads another user's role and stays as is.
   - Own-row policies (`auth.uid() = user_id` on `appointments`, `donations`, `notifications`, `messages`, ...) do not use those helpers, so add one `AS RESTRICTIVE` policy per user-facing table in `public` (a `DO` loop over `pg_tables` where RLS is enabled, plus `storage.objects`; migration `059` already uses `AS RESTRICTIVE`) with `USING`/`WITH CHECK (NOT public.is_account_blocked())`. **Exception:** `profiles` stays readable for the caller's own row (`SELECT` where `id = auth.uid()`) so the app can read `deleted_at`/`suspended_at` and sign out; every write on `profiles` is blocked.
   - Add `PERFORM public.assert_account_active();` at the top of every `SECURITY DEFINER` function granted to `authenticated` that relies only on `auth.uid()` (list them with a `pg_proc` query at the start; for example the cancel and approve/reject functions from `046` and `052`, `get_my_unread_message_count` from `061`, and every new function in tickets 05, 09, 10a, 10b, 11, 13, 14, 15, 17, 18, 19, 20 must call it).
   - Rollback: ship a reverse migration (drop the restrictive policies, restore the two helpers) and keep it ready, because a mistake here affects every user, not only blocked ones.
5. Block `deleted_at IS NOT NULL` users from showing up in staff pickers (user lists, celebrant pool, assignment) by filtering in `web/src/lib/supabase/profiles.ts` queries (around lines 246 and 266) and `UsersPage` list. Deleted User display itself is ticket 08.

Web (app-side sign-out, the second half of the cut-off): in `web/src/contexts/AuthContext.tsx` subscribe with Realtime to the signed-in user's own `profiles` row (`postgres_changes`, `id=eq.<uid>`) and re-fetch the profile when the tab regains focus (`visibilitychange`/`focus`); if `deleted_at` (ticket 19 adds `suspended_at`) is set, or the profile fetch returns nothing or a blocked error, call `signOut()` and go to `/login` with the matching message. This works because a blocked user can still read their own profile row.

Web: a **Delete user** action on `UsersPage.tsx` rows for the Super Admin only, with a confirmation modal that lists what happens (history kept, shown as Deleted User, cannot sign in, pending requests cancelled) and requires typing the user's email (same safeguard style as `TransferOwnershipModal.tsx`). Church Admin sees no delete action. Add `deleteUserAccount(userId)` in `web/src/lib/supabase/profiles.ts` and update `types/database.ts`.

**Dependency note:** Church Admin "request deletion through a ticket" is not built here; it is tickets 17 to 20 (they reuse `anonymize_user`). Suspend, the reversible alternative to Delete, is ticket 19.

- [ ] After deletion: the user cannot log in (existing session is rejected, a fresh login fails), and the same email can register again as a new account.
- [ ] Nobody can post in a Direct chat whose other participant was deleted (REST rejected with "This user is no longer available"); the history stays readable.
- [ ] **Immediate cut-off:** a user who is signed in with a still-valid access token when the Super Admin deletes them is rejected on their very next request (REST read, REST write, RPC, storage), without waiting for the token to expire; their open app tab signs them out within seconds (Realtime) or on the next focus.
- [ ] Their past appointments, donations and messages still exist and still belong to the same `user_id` / `sender_id`.
- [ ] Their pending appointment requests are cancelled; approved ones remain.
- [ ] Their open tickets are closed automatically with a system note (they are no longer waiting on anyone); tickets already closed are untouched, and a handler's view shows the note instead of an empty thread.
- [ ] A Super Admin cannot delete themselves or another Super Admin; a Church Admin or any other role calling the function is rejected.
- [ ] Deleting a Church Admin who is the last of their church is allowed for the Super Admin (the church is then without an admin; the UI warns about it in the confirmation).
- [ ] The deleted user no longer appears in staff pickers or the Users list defaults (Users list can show them under a "Deleted" filter if trivial; otherwise hidden).

**Test plan** (local `delete-user.spec.ts`): create a parishioner with an approved appointment, a donation and a sent message; delete as Super Admin through the real UI; assert with the service client that the rows survive, the profile is anonymized, `auth.users` is banned with an unusable email, login via the form fails, and the original email can sign up again. Permission cases via `clientAs`: Church Admin, Priest, self and Super Admin targets are rejected. Prove the `auth.users` update works on the local stack first; if the local Supabase rejects it, stop and report: the fallback is a service-role Edge Function (new infrastructure, needs the user's decision). Add one assertion that a parishioner's open ticket is closed with the system note. **Instant cut-off test:** sign a parishioner in with `clientAs` (keep the access token and a Supabase client built from it), delete them as Super Admin, then without refreshing assert that the same client gets no rows or an error from `appointments`, `donations`, `notifications`, `conversations`, an RPC such as `get_my_unread_message_count`, and a storage list, while the Super Admin and an unrelated parishioner are unaffected (guards the blast radius). Run the full local suite once after the restrictive policies land. Add the blocked-recipient rule (a message into a Direct chat with the deleted user is rejected by REST) and a deleted Volunteer leaving the staff channel. Eight to ten tests.
