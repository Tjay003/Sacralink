# Issue 16: Church-Owned Service Types (foundation)

Type: feature
Status: built-pending-production
Blocked by: 

---

## 1. Description
Today the services a parish offers are a fixed list of six. `appointments.service_type` is `TEXT` locked by a CHECK to `Baptism, Wedding, Funeral, Confirmation, Blessing, Other` (migration 008), and `BookAppointmentPage.tsx` hard-codes the same six in `SERVICE_TYPES`. Each church admin should be able to define the services their own parish offers. This ticket builds the data model and makes booking read the parish's own list. The management UI is ticket 06.

Settled in grilling with Tyrone (2026-10-21):
1. **Each church owns its full list.** The six built-ins are a **starter template**: every existing parish is backfilled with them, every new parish is seeded with them (alongside `seedDefaultRequirements` in `AddChurchPage.tsx` and `parishApplications.ts`). From then on a parish can rename, hide, delete or add services freely.
2. **A service type has:** a name, an optional short description (shown under the service on the booking form), a display order, and a document checklist (ticket 06). **No duration, price or icon.** Icons keep working through the existing name matching in `web/src/lib/sacramentMeta.ts`, which falls back to the generic style for custom names.
3. **Hide vs delete.** *Hide* = not offered on the booking form but kept in the parish's list and restorable. *Delete* = soft-delete (`deleted_at`): leaves the booking form and the admin list, existing appointments keep working and display normally. A service with zero appointments is physically removed.
4. **Rename follows everywhere**, including past appointments. Appointments and checklists link to the service type by id; notifications already sent keep their old wording.
5. **Names** are required and unique per church, case-insensitive, among non-deleted services.
6. **Who can write:** that parish's `church_admin`, plus `admin` and `super_admin`, enforced by RLS (not just hidden buttons). Reads are public (needed by booking, same as `sacrament_requirements`). Volunteers and priests cannot write.
7. **Web only.** Mobile is on standby and must not break (see Compatibility).

### Design
- New table `church_service_types(id uuid pk, church_id uuid fk churches on delete cascade, name text not null, description text null, display_order int not null default 0, is_hidden boolean not null default false, deleted_at timestamptz null, created_at timestamptz default now())` with a unique index on `(church_id, lower(name)) where deleted_at is null`.
- `appointments.service_type_id uuid null references church_service_types(id) on delete set null`. `appointments.service_type` (text) **stays** and is kept equal to the type's current name: drop the 6-value CHECK, and a trigger/function updates `appointments.service_type` (and `sacrament_requirements.service_type`) when a type is renamed, so existing text readers (mobile, notification SQL, dashboards) keep working untouched.
- `sacrament_requirements.service_type_id uuid null references church_service_types(id) on delete cascade`, kept alongside the legacy `service_type` text for compatibility with mobile and the AI fallback.
- Backfill (one migration, idempotent): for every existing church create the six built-ins (Baptism, Wedding, Funeral, Confirmation, Blessing, Other), then link every existing `appointments` row by `(church_id, lower(service_type))` and every existing `sacrament_requirements` row by `(church_id, lower(service_type))` (note the requirements text is lowercase and uses `wedding`, appointments use `Wedding`). Unmatched text values create a type for that church instead of leaving rows unlinked. Report counts.
- A SECURITY DEFINER function (or RLS-protected updates) for delete: soft-delete if the type has appointments, physical delete otherwise; rename updates the mirrored text columns in the same transaction.
- Rewrite every place that matches checklists/services by lowercased text to use the id where available: `BookAppointmentPage.tsx` (`SERVICE_TYPES`, `getRequirements`), `web/src/lib/supabase/requirements.ts`, `PriestDashboard.tsx` (~284, 449), `CelebrantAttentionWidget.tsx` (~248, 266), `ParishAttentionWidget.tsx`, `AppointmentsPage.tsx` funeral checks (~672, 919: keep behavior, tied to the funeral *kind*, not the literal name, so a renamed Funeral still gets burial fields; decide and document), `aiFallback.ts` (~296). Keep `sacramentMeta.ts` icon matching, and keep the priest dashboard filter chips fixed (custom types fall under "Other", as decided).
- Booking form: the service select lists the parish's non-hidden, non-deleted types in `display_order`, shows the description under the select, and a parish with no types left falls back to showing nothing bookable with a clear message. Rewire `seedDefaultRequirements` so new parishes get the six types plus their checklists (ticket 06 adds the Funeral default).

- **Old clients keep working.** Add a BEFORE INSERT trigger on `appointments` (and on `sacrament_requirements`) that fills `service_type_id` from `(church_id, lower(service_type))` when it is null. The live web build (older than `main`) and mobile insert by text only, so without this their new rows would be unlinked and invisible to id-based checklist lookups. If the text matches no type for that church, the trigger creates one rather than failing the booking.

### Compatibility and rollout

## Resolution

Built and verified on the local Docker Supabase only (full suite 154 tests, 154 passed). Production is untouched: migration 056 has not been applied to it. The web code is on `main` only.

### What was built
- **Migration `supabase/migrations/056_church_owned_service_types.sql`** (highest existing number was 055; appended to `APPLY_ALL_MIGRATIONS.sql`). ASCII only, wrapped in `BEGIN`/`COMMIT`, idempotent (a re-run applies cleanly and reports zero changes), additive and non-destructive.
  - `church_service_types(id, church_id, name, description, display_order, is_hidden, deleted_at, kind, created_at)`; unique index on `(church_id, lower(name)) where deleted_at is null`; a trigger trims names, turns a blank description into NULL and refuses to move a service to another parish.
  - `appointments.service_type_id` (`on delete set null`) and `sacrament_requirements.service_type_id` (`on delete cascade`), both nullable with partial indexes. The 6-value CHECK on `appointments.service_type` is dropped (found by definition, whatever it is named). `sacrament_requirements.service_type` was the `sacrament_type` enum on databases built from the first schema (it cannot hold custom names); it is converted to text, a no-op where it is already text (production).
  - **RLS**: public SELECT (anon and authenticated); INSERT and UPDATE only through `can_manage_church_services(church_id)`; there is no DELETE grant or policy. The same helper adds a "Parish staff can manage their checklist" policy on `sacrament_requirements`, so the parish church admin can write its own checklist (the older policy there only allowed admin and super_admin); ticket 06 builds on it.
  - **Functions** (all SECURITY DEFINER, `search_path = public`): `can_manage_church_services(uuid)`; `seed_church_service_types(uuid)` returns the parish's live services after inserting any missing starter; `delete_church_service_type(uuid)` returns `'archived'` (soft delete when appointments use it) or `'deleted'` (physical, its checklist cascades); `backfill_church_service_types()` (service_role only) returns `{churches_seeded, types_created_from_text, appointments_linked, requirements_linked}`; internal `insert_starter_service_types`, `resolve_service_type_id`, `link_service_type`, `sync_service_type_name` (not executable through the API).
  - **Link triggers** `trg_link_service_type` (BEFORE INSERT on both tables): fills `service_type_id` from `(church_id, lower(btrim(service_type)))` when null, otherwise takes the id and sets the text from the service name; an id of another parish is refused (SQLSTATE 22023). On UPDATE of the link it only validates the parish (so the backfill never rewrites text).
  - **Rename**: `trg_sync_service_type_name` (AFTER UPDATE OF name) updates `appointments.service_type` to the name and `sacrament_requirements.service_type` to the lowercased name (the established convention for requirements) in the same transaction. Past appointments follow; notifications already sent keep their wording.
  - **Backfill**: runs at the end of the migration inside the same transaction. It seeds the six for every parish with no services, then links every unlinked row by lowercased text; text that matches nothing creates a service for that parish. The migration raises (rolling everything back) if the number of appointments or requirements changed or any non-blank row is left unlinked.
- **Verification SQL (read-only)**: `supabase/verify/056_service_types_before.sql` (run BEFORE applying; totals and every distinct service text) and `supabase/verify/056_service_types_verify.sql` (run AFTER; one result set of checks with an `ok` column: churches with the six starters, null links on appointments and requirements, cross-parish links, duplicate names, triggers, CHECK dropped, RLS, plus totals to compare with the before snapshot and two commented detail queries).
- **Web**: new `web/src/lib/supabase/serviceTypes.ts` (`getBookableServiceTypes`, `getManageableServiceTypes`, `getServiceTypeByKind`, `createServiceType`, `updateServiceType`, `deleteServiceType`, `seedDefaultServiceTypes`, `isDuplicateServiceNameError`, `findServiceByName`, `isFuneralService`). `requirements.ts`: `getRequirementsForService(serviceTypeId)` replaces the text lookup; `seedDefaultRequirements` now seeds the six services through `seed_church_service_types` and writes each starter checklist by id (a service that already has documents is skipped, so calling it twice is safe); `createRequirement` and `updateRequirement` are typed (the old `any` casts and `@ts-ignore`s are gone) and accept `service_type_id`. `AddChurchPage` and `parishApplications` already go through `seedDefaultRequirements`, so new parishes get the six.
  - **Booking** (`BookAppointmentPage`): the select lists the parish's visible, non-deleted services in `display_order` (the option value is the service id), shows the description under it (`data-testid="service-description"`), loads the checklist by id, saves `service_type_id` together with the name, and keeps the chosen name when the parishioner is moved to an alternative parish. A parish with nothing bookable shows `data-testid="no-services-message"` instead of the form.
  - **Dashboards**: `PriestDashboard` and `CelebrantAttentionWidget` count required documents by `service_type_id`. `ParishAttentionWidget` picks its action and wording from the service kind (a renamed starter shows the parish's own name). `AppointmentsPage` funeral checks (Urgent badge, table and cards) use `isFuneralService`. `aiFallback` finds the parish's service of the asked kind and reads its checklist by id. `appointments.ts` exposes `service_type_id` and `service_kind` (joined from the service) on `HydratedAppointment` and sends `service_type_id` when booking. Priest dashboard filter chips and `sacramentMeta.ts` icon matching are unchanged.
  - **Types**: `web/src/types/database.ts` hand-merged (new `church_service_types` table, `service_type_id` on both tables with FKs, `sacrament_requirements.service_type` now `string`, three function entries).

### Decisions made while building
1. **Funeral kind.** A `kind` column holds the stable starter key (`baptism`, `wedding`, `funeral`, `confirmation`, `blessing`, `other`) and survives a rename; custom and text-created services have `kind` NULL. `isFuneralService(kind, name)`: a service with a kind is a funeral only if the kind is `funeral`; a service without a kind falls back to the old name match (funeral or burial). A renamed Funeral keeps its Urgent flag; a custom "Funeral Mass" still gets it.
2. **Text-created services are hidden.** Unmatched text from the backfill or from an old client creates a hidden service (so a parish that renamed or dropped a service is not forced to offer the old name again); the parish can unhide it. Text that only matches a deleted service links to that deleted row instead of creating a new one.
3. **Seeding never resurrects.** The starter insert skips a starter the parish already has by kind or by name, deleted or not. The backfill seeds only parishes that have no service rows at all, which is what makes re-running the migration safe after parishes customised their list.
4. **`admin` and `super_admin` are system-wide, `church_admin` is scoped to the parish it is assigned to** (`COALESCE(assigned_church_id, church_id)`), as the ticket says; the web "Add church" page is already open to `admin`, so the seed call has to work for any parish.
5. **Requirements text is lowercased** (`lower(name)`), the existing convention (mobile reads it with `ilike`); appointments text equals the name exactly.
6. **The link trigger normalises text on INSERT** (for example ` WEDDING ` becomes `Wedding`); the backfill leaves existing text exactly as it was.
