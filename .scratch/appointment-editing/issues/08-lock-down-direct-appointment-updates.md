# 08: Lock down direct appointment updates (approve and reject via functions)

Type: task
**Blocked by:** 02, 03, 05, 06
**Status:** resolved

**What to build:** Church staff can no longer update `appointments` directly. Approve (with optional celebrant and office note) and reject move to database functions that also write Appointment Change rows, and every web write path uses a function. After this lands, the only ways to change an approved appointment are the actions in this effort, so the change history can't be bypassed. Parishioners keep only the direct writes they have today on their own pending requests.

See spec decisions 11, 12 and ADR 0001.

- [x] Approve and reject database functions exist, are office-only, preserve today's notifications (parishioner told approved or rejected, assigned priest told of the assignment), and write Appointment Change rows.
- [x] A migration removes church admin, admin and priest roles from the appointments UPDATE policy. **Super admin keeps direct UPDATE** for system-wide admin tooling (decided 2026-10-21). Super admin edits made through the UI still go through the functions, so they are recorded in the history.
- [x] No web code path still calls a direct `update` on `appointments` for staff.
- [x] Approving, rejecting and every edit action still work end to end on web (rerun the e2e suites from tickets 01–06 plus the existing priest ministry and canon 905 suites).
- [x] A short note in the ticket resolution lists the mobile flows that now fail (mobile admin approve and update, mobile cancel), as accepted in spec decision 12.

## Resolution

- Migration `supabase/migrations/052_approve_reject_functions_and_lockdown.sql` (also appended to `APPLY_ALL_MIGRATIONS.sql`). It is idempotent (`CREATE OR REPLACE`, `DROP POLICY IF EXISTS`, constraint drop/add).
- `approve_appointment(p_appointment_id uuid, p_priest_id uuid default null, p_admin_feedback text default null)` and `reject_appointment(p_appointment_id uuid, p_admin_feedback text default null)`: SECURITY DEFINER, office of the parish (church admin or admin of the appointment's church) or super admin, `42501` otherwise; the appointment must be `pending` (`22023` otherwise). Approve sets status, `priest_id` and `admin_feedback` exactly as the web client did (a celebrant, if given, must come from the same pool the approve modal offers); reject sets status and writes `admin_feedback` only when a note is given. Notifications are those the client used to create: parishioner "Appointment Approved" / "Appointment Rejected" (types `appointment_approved` / `appointment_rejected`), and for an assigned celebrant "New Sacramental Assignment" (type `appointment`, same text as before). Each writes an `appointment_changes` row (`approve`: `{"status":"pending"}` to `{"status":"approved"}` plus `priest_id` when assigned, reason = office note; `reject`: pending to rejected). The `action` CHECK now also allows `approve` and `reject`.
- RLS on `appointments` UPDATE. Before (effective set, depending on which earlier migrations ran): "Church staff can update church appointments" (044: super admin, plus admin, church_admin and priest of the church), the older "Church admins can update church appointments" / "Admins can update appointments" (010, 012, 008), "Priests can update their assigned appointments" (031, priest of the church or assigned celebrant), the FOR ALL "Admins can manage church appointments" (001), and the parishioner policies "Users can update own pending appointments" (001) / "Users can update own appointments" (004), both `auth.uid() = user_id AND status = 'pending'`. After: only "Super admin can update appointments" (USING and WITH CHECK role = super_admin) and "Users can update own pending appointments" (the unchanged parishioner rule, one copy).
- Web: `approveAppointment` / `rejectAppointment` in `web/src/lib/supabase/appointments.ts` (rpc). `updateAppointmentStatus` and its metadata type were removed; the web no longer creates approve/reject notifications itself (no duplicates). `AppointmentsPage` approve and reject use the helpers, and Approve / Reject buttons are now shown to the parish office only (priests could click them before, but the function is office-only). `AppointmentChangeHistory` renders `approve` ("Approved", status and celebrant lines) and `reject` with the note labelled "Note:". `web/src/types/database.ts` has the two function signatures.
- Remaining direct `.from('appointments')` writes in web: none. Remaining uses are reads (`select`), the parishioner booking `insert` in `createAppointmentWithDocuments`, and nothing calls `update`, `upsert` or `delete` on appointments. Super admin uses the same functions as everyone else in the UI, so their edits are recorded in the history; they keep direct UPDATE only for tooling outside this app. `notifyUserOfStatusChange` in `notifications.ts` is no longer called by the web.
- Tests: new `web/e2e/appointment-approve-reject.spec.ts` (7 tests: approve without and with celebrant and note, payload asserted; reject payload; approve and reject only on pending; priests not offered them; database refusal keeps the request pending; history renders approve and reject). Every test asserts the browser makes no direct write (PATCH or POST) to `/rest/v1/appointments` or `notifications`. No existing spec mocked a direct approve/reject PATCH, so none needed repointing. RLS and the functions themselves cannot run in mocked e2e.
- Mobile flows that now fail (accepted, spec decision 12; mobile not modified): (1) admin approve, reject and complete in `mobile/src/lib/supabase/adminWorkflows.ts` `updateAppointmentStatus` (direct `appointments` update, used by the admin appointments screen workflow); (2) mobile cancel, `cancelAppointment` in `mobile/src/lib/supabase/appointments.ts` (direct update to `cancelled`, reason written into `notes`, called from `mobile/app/(tabs)/appointments/index.tsx`) for any staff caller; a parishioner's own cancel was already limited by the pending-only policy, whose implicit WITH CHECK rejects a row that becomes `cancelled`. These need rebuilding on `approve_appointment`, `reject_appointment`, `cancel_appointment`.
